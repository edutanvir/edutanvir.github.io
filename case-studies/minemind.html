Mine Mind.

An AI-powered mining data intelligence platform that turns Canadian public mining datasets into searchable, explainable and evidence-backed insights.

The idea

Making Canadian mining data easier to understand.

Canada publishes valuable information about its mining industry through different government datasets. These sources contain geographic information about mining features, along with monthly statistics on mineral production and shipments.

But finding useful insights means working with different formats, understanding statistical definitions, querying large datasets and knowing where the limitations are.

I built MineMind to bring these capabilities together in one application. It combines data engineering, geospatial exploration, statistical analytics and AI-powered natural-language interaction.

Instead of navigating multiple datasets manually, users can explore mining features through an interactive dashboard or ask questions and receive answers grounded in the underlying data.

The central idea

Not another chatbot that simply generates plausible answers. MineMind connects an AI model to engineered datasets and controlled analytical tools, so its answers can be traced back to data.

Why this was worth building

Two datasets. Different structures. Different meanings.

The project uses two independent Canadian public data sources. They describe different aspects of the mining industry and cannot simply be treated as one dataset.

01 · NRCan Map 900A

Natural Resources Canada provides mapped information about principal mineral areas, producing mines and oil and gas fields.

MineMind uses its geographic features and associated attributes to support mine exploration, operator searches and distance-based analysis.

What it provides: mapped features, locations, operators and available commodity information.

02 · Statistics Canada Table 16-10-0019-01

Statistics Canada's monthly statistics provide information about mineral production, shipments and inventories across Canadian geographies.

MineMind uses the table to explore commodity trends, statistical series, reporting periods and units.

What it provides: monthly statistical observations, not production records for individual mines.

An important data limitation

NRCan mapped features and Statistics Canada provincial production statistics are not joined by individual mine. Provincial nickel production cannot be attributed to a specific mine simply because that mine appears on the map.

The engineering behind it

From Canadian public data to AI-powered mining intelligence.

MineMind combines a medallion data pipeline, curated Gold Parquet datasets, read-only DuckDB analytics and Gemini-powered tools, deployed as a Streamlit application on Databricks Apps.

Build the data foundation

Prepare the NRCan and Statistics Canada datasets through the medallion pipeline and publish curated Gold Parquet data products for analytical use.

Power controlled analytics

DuckDB queries the curated Gold data. Gemini interprets questions and selects allowlisted Python tools that execute read-only analytical queries.

Deploy securely

Databricks Apps hosts the Streamlit application. GitHub provides the deployment source, while Databricks Secret Scope securely supplies GEMINI_API_KEY.

The Mine Explorer turns the geographic source data into an interactive way to investigate Canada's mining landscape.

Users can explore mapped features and inspect available attributes such as feature name, operator, city, commodity and feature type.

Geographic exploration

Visualise mapped features and understand where the recorded mining locations are.

Feature-level inspection

Application · 02

Monthly mineral production analytics.

Go beyond a commodity name. Investigate the exact statistical series, measurement unit and reporting period behind a number.

One of the important challenges in this dataset is that a commodity can have multiple statistical series. For example, nickel may be reported as concentrates, recoverable material or refined products.

These are different statistical measurements. Selecting a commodity alone is not enough to identify the correct series.

MineMind therefore uses the available series attributes, including commodity, measure, unit, vector and coordinate, to distinguish observations accurately.

Why this matters

Concentrates, recoverable and refined nickel are not interchangeable numbers. Combining them without understanding their definitions could produce misleading conclusions.

Series-level filtering

Narrow down the analysis using the statistical definitions and measurement units instead of relying on commodity names alone.

Preserving original observations

Filters can help identify useful series, while the chart retains the underlying zero and missing observations for accurate interpretation.

Application · 03

Ask MineMind.

What if exploring mining data did not require writing SQL manually?

Ask MineMind integrates Google's Gemini API with a set of Python functions that act as controlled analytical tools.

The model interprets the question, selects an appropriate tool, and receives the structured result. It then explains the returned information in natural language.

The AI does not receive unrestricted access to the database. The available tools use read-only DuckDB connections and parameterised SQL queries.

A question worth asking

Can we understand the mining landscape around Sudbury?

A demonstration question for Ask MineMind:

"Identify all mapped mining features within 50 km of Sudbury, group them by operator, and explain how Ontario's nickel production has changed over the last 36 months. Distinguish the different nickel product series and explain what the data cannot tell us about production at individual mines."

This question combines spatial analysis, operator information, provincial production statistics and responsible interpretation. It also tests whether the AI understands the difference between a mapped mine feature and a provincial statistical total.

Engineering in practice

Building it meant solving real problems.

The interesting part was not just getting the application to work. It was understanding why something failed and isolating the problem before changing the code.

01 · Investigating unexpected statistical values

While exploring Statistics Canada's mineral production data, I noticed that some geographic and commodity combinations contained many zero values.

Instead of immediately treating these as missing data or changing the ETL logic, I traced the observations back to the original CSV files.

For example, the Alberta Gold series contained observations that were zero in the source records as well as in the analytical database. This established that the values were not introduced by the ingestion process.

I also examined the statistical status symbols to distinguish reported zeros from unavailable or suppressed values.

The lesson

A zero is not automatically a missing value. A missing or suppressed observation is not automatically zero. Data-quality decisions must be based on source definitions and evidence.

02 · Finding the correct statistical series

Another challenge appeared in the production analytics filters. Selecting a commodity alone could expose several distinct statistical series.

I investigated the original source attributes, including commodity, unit, vector and coordinate, to identify the exact series.

I also separated the logic used to populate dashboard choices from the data used to display the time series. This allowed the interface to avoid presenting zero-only series as useful default choices without removing the original zero and missing observations from the analytical chart.

03 · The Ask MineMind request that never returned

When I first tested the conversational assistant, a simple question about mining features within 50 km of Sudbury remained stuck at "Querying the data..."

Rather than immediately rewriting the Gemini integration, I tested the database tool independently.

First: isolate the database query

I called the mines_near_place Python function directly, bypassing Gemini and Streamlit's conversational workflow.

The DuckDB query completed in 0.08 seconds and returned 10 mapped features within 50 km of Sudbury.

Second: isolate the Gemini connection

I tested a basic text-generation request without any database tools. The request also remained pending.

I added an explicit 30-second timeout to capture the underlying error instead of waiting indefinitely.

What this investigation established

The database query was working. The basic request to the original model was timing out, while the alternative model responded successfully. Switching the configured model resolved the immediate application issue.

This did not prove that the original model is always slower or that function calling itself was defective. It isolated the immediate failure to the original model request in that test.

04 · Why I prefer evidence over quick fixes

These investigations reinforced an important engineering habit: isolate the components before changing the system.

  • Test the database independently.
  • Test the external API independently.
  • Capture the actual error with a timeout.
  • Compare model behaviour using the same request.
  • Change only the component supported by the evidence.

A working application is important, but understanding why it works and why it fails is just as important.

Beyond a conventional chatbot

What makes MineMind different?

The value is not simply that an AI model can answer a question. It is that the application gives the model access to a carefully engineered analytical environment.

Data-grounded answers

Answers are supported by queries against curated Gold datasets rather than relying exclusively on general model knowledge.

Spatial intelligence

Users can explore geographic relationships between mapped mining features and selected locations.

Statistical awareness

The application distinguishes statistical series, units, missing values, suppressed observations and reported zeros.

Controlled tool execution

Gemini receives a defined set of Python functions that query the database through read-only connections and parameterised SQL.

Traceable responses

The Tools used panel exposes the analytical functions called, their arguments, returned row counts and source information.

Responsible interpretation

The AI is instructed not to attribute provincial production totals to individual mines or invent unavailable values.

How would MineMind compare with a general AI model?

MineMind is not intended to prove that its underlying language model is inherently more intelligent than other models.

Its advantage is the combination of domain-specific data, engineered analytical tools, explicit statistical rules and traceable results.

A fair comparison would give a general-purpose model the same questions without access to MineMind's database, then compare both systems against verified source records.

The evaluation would measure factual accuracy, data grounding, statistical interpretation, source traceability and unsupported claims.

The goal is not to make AI sound knowledgeable about mining. It is to make mining data accessible without losing the evidence behind an answer.

Engineering reflection

What building MineMind taught me.

This project brought together several parts of data engineering that are often treated separately: ingestion, data modelling, SQL analytics, geospatial data, application development and AI integration.

More importantly, it showed me that the hardest part is not always writing code. It is understanding the source data, validating its meaning and deciding what conclusions the data can actually support.

  • Data quality starts at the source: investigate original observations before changing transformation logic.
  • Statistical definitions matter: identical commodity names do not necessarily represent identical measurements.
  • AI needs boundaries: controlled tools and reliable data access matter more than simply connecting an API.
  • Debugging needs isolation: independently test each component before changing the architecture.

What's next

Where I'd take MineMind next.

MineMind is a foundation for a more comprehensive Canadian mining intelligence platform. There are several areas I would develop further:

  • More public data sources: introduce additional verified datasets where their definitions and relationships can be established.
  • Stronger data-quality monitoring: automate checks for missing values, unusual observations, duplicate records and changes in source structures.
  • AI evaluation: create a benchmark of domain-specific questions to measure accuracy, tool selection, response quality and source grounding.
  • Production readiness: improve API timeout handling, monitoring, caching, security and deployment reliability.
Good data engineering makes information usable. Good AI makes it easier to explore. Trustworthy intelligence requires both.
